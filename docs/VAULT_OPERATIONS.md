# Local encrypted password operations

The user selected local server-side AES-256-GCM on 1 November 2026 to remove the OpenBao service and its unseal/AppRole requirements. Deployment evidence is recorded below after actual verification.

## Key handling

The installer creates /opt/workstel/keys/vault-keyring.json using the operating system random generator: one 256-bit key, active ID k1. The directory is 0700 and the file is 0600. Existing keys are never regenerated by reinstalling. Docker Compose mounts the file as a read-only secret at /run/secrets/workstel_vault_keyring. The startup wrapper reads it into process memory via WORKSTEL_VAULT_KEYRING because user workers cannot read arbitrary host files. The value is absent from Compose environment configuration but accessible to trusted server/container administrators through process memory/environment. Never print it, commit it, or bundle it with releases or frontend assets.

Encryption uses Web Crypto AES-GCM, a random 96-bit nonce per write and a 128-bit authentication tag. Authenticated data binds the format, key ID, hotel, account and owner. The stored format is workstel:aesgcm:v1:KEY_ID:BASE64_NONCE_CIPHERTEXT_TAG. Keys remain outside PostgreSQL. Full server compromise can expose the key and passwords; this provides less key isolation than a separate KMS.

## Deployment

On the existing hotel server, install Debian python3-cryptography for the one-time legacy conversion, then run python3 infra/switch_local_encryption.py from the reviewed release. It backs up the database and legacy key-manager files into a restricted server directory, disables secrets, preserves and verifies every legacy encrypted row, applies migration 202611010005 transactionally, and installs the function plus additive Compose overlay. It never deletes password records. If interrupted, keep secrets disabled and inspect the protected backup locally; do not blindly rerun after application credentials have been replaced.

Run python3 infra/commission_secret_service.py --email YOUR_APPROVED_ADMIN_EMAIL interactively. The --operator option is available to server administrators: it creates a fictional password-authenticated test identity in the selected operator's scope, exercises actual HTTPS operations, then disables/bans the test identity while preserving archived records and audit evidence. It never sends email or changes the real staff member's password. Failed commissioning disables secret operations again.

Always recreate functions with all four Compose files: docker-compose.yml, docker-compose.local.yml, docker-compose.workstel-auth.yml, docker-compose.workstel-vault.yml. The wrapper preserves the installed runtime command. Startup requires no manual unseal or expiring AppRole credential.

Remove the old workstel-openbao container only after HTTPS acceptance and a function restart test pass. Retain its encrypted recovery archive solely for rollback until backup retention permits deletion; active operations must not depend on it.

## Backup, recovery and rotation

Back up the PostgreSQL dump and versioned keyring to separately protected off-VM storage. A database backup alone cannot recover passwords. Losing both the VM and local keyring loses access. Do not claim disaster recovery until an isolated restore of both has passed.

To rotate, generate a new independent 32-byte key on the server, add a new key ID and select it as active. Keep all old keys while any row or retained backup uses them. Replace the file atomically with permissions 0600 and recreate functions. New writes use the new key; existing ciphertext remains readable with its stored key ID. Rotation does not automatically re-encrypt old rows. Never remove an old key without a verified re-encryption/backup-retention procedure.

Authorization, five-minute recent authentication, rate limits, idempotency, conflict checks and durable reveal auditing remain mandatory. Decryption failure, missing keys or audit failure release no password. No plaintext is stored in browser persistence.

## Remaining acceptance

Off-VM backup, isolated restore and sharing with a second real staff account require separate verification. Existing host boot ordering can still prevent the API gateway binding its private IP; removing OpenBao does not resolve that infrastructure issue.
